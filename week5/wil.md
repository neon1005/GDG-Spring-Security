**AT의 만료시간 딜레마(access token):**  
만료시간이 짧다면 토큰이 탈취되더라도 무용지물이 된다.  
사용자 경험(UX)에서는 안좋다. 재로그인 빈도 높으므로  
만료시간이 길다면 AT의 경우 노출빈도가 높아 보안이 취약하다.  
  
--> 만료시간이 짧으면서도 재로그인 빈도를 낮추는 매커니즘이 필요하다.  
  
Refresh Token:  
보안과 사용자 경험을 모두 만족시킬 수 있는 토큰  
토큰의 수명이 길다  
일반적인 api 호출에는 사용되지 않음  
access token이 만료됐을때 새로 받아오는 용도로만 쓰인다. 노출 빈도가 낮다.  
  
역할 분리와 흐름:  
1. 사용자 로그인, 서버는 AT/RT 응답    
2. 사용자 모든 API 요청에 AT가 사용, RT는 보관  
3. AT 만료로 인해 API 호출 실패(401 Unauthorized)  
4. RT 서버의 재발급 엔드포인트로 전송해 AT 재발급  
5. 서버는 RT 검증 및 새 AT 발급  
6. 클라이언트는 새 AT로 API 호출 재시도 - 만료되었는지 경험 못함  
7. RT만료 후 재로그인  
  
문제점:  
RT가 탈취된다면 RT의 긴 수명동안 공격자가 활용가능하고 RT로 무한정 AT 발급이 가능하다.  
정상 사용자도 RT를 사용하기 때문에 공격을 탐지할 수 없다.  
  
이 문제를 해결하기 위한  
**RTR(Refreshs Token Rotation):** 모든 RT를 일회용으로 사용  
1. 클라이언트가 RT로 새로운 AT요청  
2. 이때 새 AT뿐만 아니라 새 RT도 발급  
3. 이전 RT는 무효화
