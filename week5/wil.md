**AT의 만료시간 딜레마(access token):**  
- 만료시간이 짧다면 토큰이 탈취되더라도 무용지물이 된다.   
- 재로그인 빈도 높으므로 사용자 경험(UX)에서는 안좋다.   
- 만료시간이 길다면 AT의 경우 탈취되었을 때 사용할 수 있는 시간이 길어 보안에 취약하다.  
   
**-->** 만료시간이 짧으면서도 재로그인 빈도를 낮추는 매커니즘이 필요하다.  
   
**Refresh Token: 보안과 사용자 경험 사이의 균형을 맞출 수 있는 토큰**  
**특징:**  
- 토큰의 수명이 길다.  
- 일반적인 api 호출에는 사용되지 않는다.  
- access token이 만료됐을때 새로 받아오는 용도로만 쓰인다. (노출 빈도가 낮다)  
  
**역할 분리와 흐름:**  
1. 사용자 로그인, 서버는 AT/RT 응답    
2. 사용자 모든 API 요청에 AT가 사용, RT는 보관  
3. AT 만료로 인해 API 호출 실패(401 Unauthorized)  
4. RT 서버의 재발급 엔드포인트로 전송해 AT 재발급  
5. 서버는 RT 검증 및 새 AT 발급  
6. 클라이언트는 새 AT로 API 호출 재시도 - 만료되었는지 경험 못함  
7. RT만료 후 재로그인  
  
**문제점:**    
RT가 탈취된다면 RT의 긴 수명동안 공격자가 활용가능하고 RT로 무한정 AT 발급이 가능하다.  
일반적인 RT 방식에서는 탈취된 RT와 정상 사용자의 RT가 구분되지 않기 때문에 공격 탐지가 어렵다.  
   
이 문제를 해결하기 위한   
**RTR(Refresh Token Rotation): 모든 RT를 일회용으로 사용**  
1. 클라이언트가 RT로 새로운 AT요청  
2. 이때 새 AT뿐만 아니라 새 RT도 발급  
3. 이전 RT는 무효화  
  
**RTR의 공격 탐지:**  
정상 사용자의 RT1 이 탈취되었다고 가정)  
1. 공격자는 RT1 으로 새 AT2 및 RT2 발급
2.  정상 사용자가 RT1 으로 재발급 요청  
3. 이미 사용된 RT1 감지  
4. 이미 사용된 RT가 다시 사용되면 서버는 RT 탈취 가능성이 있다고 판단
5. 해당 사용자에게 발급된 토큰 패밀리(token family) 전체를 무효화한다.  
6. 사용자, 공격자 재로그인 필요 - 공격자는 (비밀번호 모르면) 재로그인 불가  
  
**RTR 구현시 서버가 알아야 하는 것:**  
1. 어떤 RT가 현재 유효한가  
2. 어떤 RT가 이미 사용됐는가  
  
서버에 RT 정보 저장해야하는데 어떤 저장소 프로그램을 사용할까? 
**RDB(디스크 기반 관계형 DB) VS Redis(인메모리 KV 스토어)**
**응답 속도(읽기/쓰기 지연):**   
단순 토큰 조회/저장 작업에선   
Redis(인메모리) > RDB(디스크 기반)  
  
**자동 만료(Time To Live TTL):**  
RDB: 만료된 토큰 정리하는 스케줄러 만들어야함 - 운영 코드 중가  
Redis: TTL 설정 지원  
  
**영속성 부담:**    
RT는 영구 보관 대상이 아니고 만료 시간이 있는 데이터이므로 TTL 관리가 쉬운 Redis와 잘 맞는다.  
  
**부하 문제(트래픽 처리 적합도):**  
RT 재발급 빈도가 많은 사용자에게 누적되면 부하가 높을 수 있다.  
잦은 갱신에 부하가 누적되는 RDB.  
빈도가 높은 Key 값 관리에 최적화된 Redis.  

   
서버에 RT 정보 저장한다는 것은 Stateless 가 부분적으로 깨지는 것을 의미한다.  
API 요청에는 AT만 검증 대상이되고 Stateless 하다.  
RT 재발급 처리에는 Stateful 하다.
  
**OAuth2.0: 외부 서비스의 권한 위임 흐름을 통해 특정 리소스에 접근할 수 있도록 하는 인가 프로토콜**    
구글, 카카오 등 신뢰할 수 있는 외부 서비스를 통해 신원을 증명한다.  
수많은 앱, 웹에서 보면 'Google 로 로그인' 의 정체가 OAuth2.0 이었다.  
    
  
호텔 카운터(구글, 카카오)에서 한 번 체크인을 받으면  
그 출입증 가지고 호텔의 각종 서비스 시설을 이용할 수 있다.  

사용자의 로그인 흐름을 편하게 만들어준다.    
서버는 사용자의 비밀번호를 묻지도 않고 알지도 못한다.  
  
**OAuth2.0 편의성:**  
사용자 입장: 불필요한 회원가입 과정없고 기억해야할 비밀번호가 줄어든다, 잘 알려진 인증 주체를 통한 신뢰감 형성.  
운영자 입장: 가입 단계 단축, 보안 사고 책임 분산. 
    
**OAuth2.0 흐름:**  
(볼드체가 아닌 것은 SpringSecurity, Google 등에서 해주는 기능)  
**1. 사용자가 Google로 로그인 클릭**   
2. 우리서버(OAuth Client)는 로그인 요청을 Google Auth Server로 Redirect  
**3. Auth Server는 사용자 브라우저를 Google 로그인 페이지로 Redirect**    
**4. 사용자는 Google 로그인 화면에서 직접 로그인**    
**5. Auth Server는 사용자를 우리 서버로 Redirect. 이때, URL 파라미터 임시 Auth Code 발급(수명짧고 한 번 사용시 만료)**  
6. 우리 서버는 Auth Code로 Google Auth Server에 AT 요청(client id, client secret, redirect uri 등을 함께 보냄)
7. Auth Server 가 Auth Code 검증  
8. Auth Server 가 우리 서버에 AT 발급  
9. 우리 서버는 AT로 Google Resource Server에 사용자 정보 요청 - 이메일, 이름  
10. Resource Server 는 사용자 프로필 정보 응답   
**11. 우리 서버는 해당 프로필 정보로 적절한 인증 처리**  
    **신규 유저라면 해당 사용자 생성**  
    **기존 유저라면 토큰/세션 발급**

**OAuth2.0 도입 시 개발자가 할 일:**
Google Cloud Console 에서
- OAuth 프로젝트 생성
- 우리 서비스 등록(secret key 발급용)
- Redirect URI 등록
- scope 설정(요청할 권한 범위)

우리 서버에서
- client secret(secret key) 안전 보관
- 자체 인증 상태로 전환

**다양한 인증 방식 조합의 특징:**
자체 회원가입 + 세션 방식: 구현 직관적, 소규모 서비스 적합, 토큰 탈취 후 장기간 악용 문제 제어 쉬움
자체 회원가입 + 토큰 방식: Scale Out 환경에 적합
OAuth + 세션 방식: 외부 로그인을 통한 단순화. 토큰 탈취 후 장기간 악용 문제 제어 쉬움
OAuth + 토큰 방식: 외부 로그인을 통한 단순화. Scale Out 환경에 적합


**OIDC(OpenID Connect) 방식: OAuth 2.0을 기반으로 만들어진 유저의 인증(Authentication)에 초점을 맞춘 프로토콜**

OAuth2.0 기반으로 만들어졌기 때문에 타사(google, 카카오)의 계정으로 인증이 가능하고 기본적인 유저 정보를 받을 수 있다는 점이 동일하다. 마찬가지로 OAuth2.0 흐름과 거의 비슷하다.

**차이점은** 인증서버가 우리 서버(Client)에게 AT를 발급해줄 때 **ID token을 같이 발급해준다.**
인증 결과를 담은 ID token을 통해 클라이언트는 유저를 인증하거나 간단한 프로필을 만들 수 있다.

**ID token:**
ID token 은 JWT의 형식으로 전달된다.

토큰을 담을 scope의 범위가 정해져 있고
payload에 담을 Claims의 이름도 표준화되어
OIDC를 사용하는 여러 서비스들의 규격을 하나로 통일할 수 있다는 장점이 있다.
  
**OAuth VS OIDC 차이점 정리:**  

|구분|OAuth2.0|OIDC|  
|---|---|---|
|용도|인가|인증| 
|관심사|리소스 접근 권한|사용자 신원 확인|
|리턴값|only AT(리소스 접근용)|ID token + AT(유저정보 포함)|
|사용자 정보|AT로 UserInfo API 호출|ID token 사용|


OAuth를 통해 유저 정보를 얻기 위해서는 AT를 발급받은 후 다시 AT 토큰으로 유저의 정보를 요청하는 작업을 해야하지만,
OIDC에서는 ID Token에 사용자 식별 정보가 포함되므로, 간단한 로그인 처리에서는 별도의 사용자 정보 API 호출을 줄일 수 있다.

**OAuth 를 인증의 목적으로 사용시 문제점:**
1. OAuth2.0의 Access Token은 리소스 접근 권한을 나타내는 토큰이므로, 클라이언트가 표준화된 방식으로 사용자의 신원을 확인하기 어렵다.
2. Access Token은 특정 리소스 접근 권한을 나타내는 토큰이지, 클라이언트에게 사용자의 인증 결과를 알려주기 위한 토큰이 아니다.
3. Access Token은 Refresh Token을 통해 재발급될 수도 있으므로, Access Token의 존재만으로 사용자가 방금 인증했다는 의미를 보장하지 않는다.
4.OAuth2.0의 Access Token은 클라이언트 인증용 토큰이 아니므로, 클라이언트가 이 토큰이 자신을 대상으로 발급된 인증 결과인지 판단하기 어렵다.
