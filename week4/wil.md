-사용자 규모가 커지면  
세션 기반 인증 -> 각 사용자마다 세션 객체 생성 -> 용량, 검색에서 부담  
토큰 기반 인증-> 서버가 사용자별 인증 상태를 세션처럼 직접 저장하지 않음 -> 외부 세션 저장소 관리 부담 없음(비교문은 가벼운 연산)  
ex. JWT 서명 검증은 CPU 연산으로 검증하는 방식, 메모리는 각 토큰의 파싱에만 잠시 쓰임  
결국 인증 계층에서 낭비되는 메모리를 줄이고자 서버가 Stateless 하도록하는 토큰 인증 방식 채택  서버 자원 무중단 배포  
  
사용자 규모가 작다면  
인증 계층에서의 메모리 부담이 안되므로 다른 이점이 많은 세션 인증 방식 채택 - 학생 수준 프로젝트  

Scale Out: 트래픽이 많아질 때 동일한 역할을 수행하는 서버 인스턴스를 수평으로 추가하는 확장 전력  
vs Scale Up: 기존 서버의 CPU, 메모리를 향상  
특징:  
a. load balancer(로그인 요청서버 != 다음 요청 서버) 앞에다 두고 여러 서버에 요청을 골고루 나눠줌.
   -> 한 사용자의 서로 다른 요청이 다른 서버로 갈 수 있음 
b. 인스턴스 간 메모리 비공유 (각각 독립적을 존재): 서로 메모리 참조가 불가능  
c. 동적 인스턴스 증감(auto scaling): 비용 절약 측면  
결국, "토큰 인증 방식" 서버가 인증 상태를 저장 안하므로 토큰 검증 로직만 동일하게 가져가면 된다  
서버 a에서 서버 b가 검증 가능하다 서명 검증에 사용하는 비밀키만 동일하게 배포 MSA, Cloud 환경 유용

Scale Out 에서 세션 방식을 사용하고자 한다면 서버 a 메모리에 세션 등록이 된다면 load balancer가 서버 b로 요청을 보냈을떄
서버 b에서 이를 참조할 수 없다.
해결방법 3가지:  
a. Sticky Session(특정 사용자 요청을 항상 같은 서버로) 트래픽이 몰리는 불균형이 생길 수 있다.  
b. Session Clustering 서버 세션이 변경될 때 마다 서버간 세션 데이터 복제 - 서버 수가 늘어날 수록 트래픽 급증  
c.External Session Storage 외부 세션 저장소 운영 - 관리 난이도가 높다  
  
세션의 장점  
보안 위협 3가지  
a. Hijacking(세션 ID, 토큰 가로채기)  
b. Escalation (인증 정보를 조작하여 권한 상승)  
c. 내부자 위협 (퇴사자가 퇴사 후에도 시스템 접근 가능)  

세션 인증은 인증 정보가 서버에 존재하여 서버가 제어권을 가지고 보안 사고 감지 시 세션 즉시 비활성화 가능  
관리자 강제 로그아웃, 비밀번호 변경 후 기존 로그인 세션 제거, 의심 계정 차단 같은 기능을 구현하기 쉽다.  
  
토큰 인증의 가장 큰 약점: 토큰 인증은 즉시 무효화 어려움  위변조 여부만 검증하고 유효한 상태인지 검증 안함  
만료시간 이전까지는 무효화 어려 - 블랙리스트 운영시 stateless 방식의 장점이 사라짐    
  
세션 방식이 스프링 시큐리티 기준 프레임워크가 대부분을 자동으로 처리해주기 때문에 개발이 편리하다  
토큰인증은 개발자가 구현할 것이 많다 ex) customfilter 로직  
  
서버 성능 지표  
응답시간, 메모리 사용량, 네트워크 오버헤드(인증 과정에서 발생하는 추가적 통신)  
  
세션 인증의 성능 영향  
메모리 사용량 (내부 세션 저장소), 네트워크 오버헤드(외부 세션 저장소 운영의 경우)  
  
토큰 인증의 성능 영향  
응답 시간(검증 연산)  

결정적으로 실무에서는 하이브리드 전략을 쓴다(Access Token + Refresh Token //약간의 stateful로 제어권 가지기)  
  
개인 회고 - 할 프로젝트에서 어떤 인증 방식을 적용할 것인지    
   
학교 전자출결 앱에서 응답 시간이 너무 느려 긴박하게 출결을 해야할 때 난처함을 겪었다. 트래픽이  
일시적으로 급증한 것일 수도 있지만(원인을 단정할 순 없지만)  
사용자 규모가 늘어나고 Scale Out관점에서는 토큰 인증 방식이 더 적합할 수 있겠다고 생각했다.  
  
실무에서 신규 런칭하는 서비스에서 초창기 사용자가 적을 때 세션 인증 방식으로 이점을 챙기다가 시간이 지나 사용자가 급증하면
토큰 인증 방식으로 전환할 수 있는지 궁금했다.  
서비스 초기에 세션으로 시작하고 나중에 토큰으로 전환하는 것은 가능하지만,   
인증 방식이 바뀌므로 프론트엔드와 백엔드 모두 수정이 필요하다는 것을 알았다.  
이는 개발의 어려움을 초래할 수 있어 Scale Out, 외부 API연동성이 크다면 처음  부터 토큰 기반 또는 하이브리드 방식을  
채택하는 것이 좋겠다 생각했다.
